REST API TblFlow дає доступ до тих самих даних, що й інтерфейс, з правами особи або облікового запису, який виконує запит. Усі його маршрути починаються з `/api/`. Ця сторінка описує чотири способи автентифікації, а потім вхідні webhook.

| Потреба | Спосіб |
|---|---|
| Скрипт або інструмент для себе | Персональний токен доступу |
| Сторонній застосунок, що діє від імені користувачів | Застосунок OAuth |
| Скрипт, інтеграція або CI без прив'язки до особи | Службовий обліковий запис |
| Зовнішній інструмент, що запускає автоматизацію або агента | Вхідний webhook |

Токени надсилаються в заголовку `Authorization: Bearer <токен>`.

## Персональні токени доступу

Персональний токен доступу діє з вашими правами й обмежений областями та просторами або базами, які ви обираєте. Ви можете надати доступ лише до баз і просторів, до яких маєте доступ самі.

У своїх особистих налаштуваннях відкрийте **Персональні токени доступу**, а потім **Створити новий токен**:

- **Назва** і **Опис**;
- **Термін дії**: 7, 30, 60, 90 або 365 днів, або власна дата. Жоден токен не живе довше 365 днів;
- **Області**: дозволені дії;
- **Доступ**: одна база, один простір (усі його поточні та майбутні бази) або **Усі ресурси**.

Токен показується лише один раз: скопіюйте його одразу. **Оновити токен** створює новий, і скрипти, які використовують старий, потрібно оновити. Після видалення токена скрипти, які його використовують, більше не мають доступу до API. Електронний лист попереджає вас до закінчення терміну дії (за 14 і 3 дні); він ніколи не містить токена.

| Дія | Маршрут |
|---|---|
| Переглянути, створити | `GET` і `POST /api/access-token` |
| Змінити, видалити | `PUT` і `DELETE /api/access-token/:accessTokenId` |
| Оновити | `POST /api/access-token/:accessTokenId/refresh` |

## Конструктор запитів API

На сторінці токенів посилання **Конструктор запитів API** відкриває `/developer/tool/query-builder`. Оберіть базу та таблицю, налаштуйте вигляд, пошук, фільтр, сортування та формат комірок: вкладка **Конструктор API** сформує запит і попередній перегляд значення, яке повертається. Вкладка **Контекст ШІ** створює текст для копіювання у ваш ШІ-асистент, у повній або скороченій версії, щоб він розумів, як працювати з таблицею.

## Документація OpenAPI

Застосунок генерує опис OpenAPI для свого API і публікує його за адресами `/docs` (Swagger) та `/redocs` (Redoc), якщо на сервері не вимкнено документацію.

## Застосунки OAuth

Застосунок OAuth дозволяє сторонньому сервісу запитувати доступ до облікового запису ваших користувачів. У своїх особистих налаштуваннях відкрийте **Застосунки OAuth**, а потім **Новий застосунок OAuth**:

- **Назва застосунку OAuth**, **Опис**, **URL домашньої сторінки**, **Логотип**;
- **URL зворотного виклику** (можна кілька): адреса, на яку повертається користувач після того, як авторизував застосунок;
- **Області**: дозволи, яких потребує застосунок;
- **Секрети клієнта**: **Згенерувати новий секрет клієнта**. Секрет видно лише під час створення. Кожен секрет показує дату останнього використання.

**ID клієнта** видно на сторінці застосунку. Потік є кодом авторизації OAuth 2.0:

1. Застосунок перенаправляє користувача на `GET /api/oauth/authorize` (з `client_id` і `response_type`).
2. Користувач входить в систему, бачить повідомлення «{назва} запитує доступ до вашого облікового запису» з потрібними областями, а потім обирає **Авторизувати**.
3. Застосунок обмінює код на токени через `POST /api/oauth/access_token`, автентифікуючись за своїм клієнтом. Токен оновлення дозволяє отримати новий.

Користувач бачить застосунки, яким він надав доступ, у **Профіль → Безпека → Авторизовані застосунки**, і може відкликати їм доступ (кнопка відкликання).

| Дія | Маршрут |
|---|---|
| Переглянути, створити застосунок | `GET` і `POST /api/oauth/client` |
| Прочитати, змінити, видалити | `GET`, `PUT` і `DELETE /api/oauth/client/:clientId` |
| Створити або видалити секрет | `POST /api/oauth/client/:clientId/secret`, `DELETE …/secret/:secretId` |
| Відкликати доступ усіх користувачів | `POST /api/oauth/client/:clientId/revoke-access` |
| Відкликати власну авторизацію | `POST /api/oauth/client/:clientId/revoke-token` |
| Переглянути авторизовані застосунки | `GET /api/oauth/client/authorized/list` |

[Сервер MCP](/uk/docs/mcp-server) і [CLI](/uk/docs/cli) також працюють через OAuth-сервер TblFlow.

## Службові облікові записи

Службовий обліковий запис надає скрипту, інтеграції або CI доступ до простору, який не залежить від жодної особи. Він є учасником простору з обраною роллю (ніколи не власником), не займає місця ліцензії, а його токени діють лише для цього простору.

Сторінка доступна лише власникам простору: **Налаштування простору → Безпека та аудит → Службові облікові записи**.

1. Введіть **Назву облікового запису** та оберіть **Роль**: **Читач**, **Редактор** або **Творець**, потім **Створити обліковий запис**.
2. Щоб випустити токен, вкажіть **Назву токена**, **Доступ** (**Лише читання**, **Читання та запис записів** або **Усе, що дозволяє роль**) і **Термін дії** 30, 90, 180 або 365 днів, а потім **Випустити токен**.
3. Скопіюйте токен: його більше ніколи не буде показано.

Фактичний доступ є перетином областей токена та ролі облікового запису. **Відкликання** токена або **Видалення** облікового запису набирає чинності одразу після підтвердження. Простір може мати не більше 50 службових облікових записів, а обліковий запис — не більше 20 токенів. Кожне створення, зміна ролі, випуск і відкликання записується в журнал простору, а власники отримують електронний лист до закінчення терміну дії токена. [CLI](/uk/docs/cli) використовує їх у безперервній інтеграції.

| Дія | Маршрут (власник простору) |
|---|---|
| Переглянути, створити | `GET` і `POST /api/space/:spaceId/service-account` |
| Змінити роль, видалити | `PATCH` і `DELETE /api/space/:spaceId/service-account/:serviceAccountId` |
| Випустити токен | `POST …/:serviceAccountId/token` (`name`, `scopes`, `expiredTime`, необов'язково `baseIds`) |
| Відкликати токен | `DELETE …/:serviceAccountId/token/:accessTokenId` |

## Вхідні webhook

### Запуск автоматизації

[Автоматизація](/uk/docs/automations), для якої тригером є **Коли отримано webhook**, запускається HTTP-запитом:

```bash
curl -X POST "https://app.tblflow.com/api/base/<baseId>/workflow/<workflowId>/webhook" \
  -H "X-Webhook-Secret: <secret>" \
  -H "Idempotency-Key: commande-4821" \
  -H "Content-Type: application/json" \
  -d '{"client": "Ada", "montant": 120}'
```

- Адреса відображається в редакторі автоматизації та в **Автоматизувати → Webhooks** з кнопкою **Копіювати адресу**.
- Секрет є обов'язковим. Без правильного `X-Webhook-Secret` запит отримує помилку 401. Ідентифікатора автоматизації недостатньо для автентифікації.
- `Idempotency-Key` (або `X-Idempotency-Key`, не більше 255 символів) не дає обробити одну й ту саму подію двічі: тоді відповідь містить `duplicate: true`.
- Відповідь має вигляд `{ "received": true, "queued": true, "eventId": "…" }` одразу після того, як подію збережено. Якщо збереження не вдалося, сервер відповідає 503: повторіть спробу.
- Тіло JSON читається на верхньому рівні в кроках автоматизації.
- Якщо автоматизацію вимкнено, запит відповідає `{ "received": true, "steps": 0 }` і нічого не виконує.

Кожен прийнятий виклик враховується в місячній квоті запусків автоматизацій.

### Запуск агента

[Агент](/uk/docs/ai-agents) також може мати тригер **Вхідний webhook**. Запит має вигляд `POST /api/agent/:agentId/webhook` із заголовком `X-Agent-Secret` і тілом JSON. Недійсний секрет отримує помилку 401. Відповідь — `{ "received": true }`, після чого агент виконується; виклик витрачає квоту запусків агента.
