REST API TblFlow даёт доступ к тем же данным, что и интерфейс, с правами того человека или аккаунта, который делает запрос. Все его маршруты начинаются с `/api/`. На этой странице описаны четыре способа аутентификации, а затем входящие вебхуки.

| Задача | Способ |
|---|---|
| Скрипт или инструмент, принадлежащий вам | Персональный токен доступа |
| Стороннее приложение, которое действует от имени пользователей | OAuth-приложение |
| Скрипт, интеграция или CI, не связанные с конкретным человеком | Сервисный аккаунт |
| Внешний инструмент, который запускает автоматизацию или агента | Входящий вебхук |

Токены передаются в заголовке `Authorization: Bearer <токен>`.

## Персональные токены доступа

Персональный токен доступа действует с вашими правами и ограничен областями применения и пространствами или базами, которые вы выбираете. Вы можете предоставить доступ только к базам и пространствам, к которым имеете доступ сами.

В личных настройках откройте **Персональные токены доступа**, затем **Создать новый токен**:

- **Имя** и **Описание**;
- **Срок действия**: 7, 30, 60, 90 или 365 дней либо произвольная дата. Ни один токен не живёт дольше 365 дней;
- **Области применения**: разрешённые действия;
- **Доступ**: одна база, пространство (все его текущие и будущие базы) или **Все ресурсы**.

Токен показывается только один раз, скопируйте его в этот момент. **Восстановить токен** создаёт новый, и скрипты, использующие старый, нужно обновить. После удаления токена скрипты, которые его использовали, больше не получают доступ к API. За 14 и 3 дня до истечения срока вам приходит письмо; в нём никогда не содержится сам токен.

| Действие | Маршрут |
|---|---|
| Список, создание | `GET` и `POST /api/access-token` |
| Изменение, удаление | `PUT` и `DELETE /api/access-token/:accessTokenId` |
| Восстановление | `POST /api/access-token/:accessTokenId/refresh` |

## Конструктор API-запросов

Со страницы токенов ссылка **Конструктор API-запросов** открывает `/developer/tool/query-builder`. Выберите базу и таблицу, настройте представление, поиск, фильтр, сортировку и формат ячеек: вкладка **Конструктор API** построит запрос и покажет предпросмотр возвращаемого значения. Вкладка **Контекст ИИ** создаёт текст для копирования в ваш ИИ-ассистент, в полной или компактной версии, чтобы он понимал, как работать с таблицей.

## Документация OpenAPI

Приложение генерирует описание OpenAPI своего API и публикует его по адресам `/docs` (Swagger) и `/redocs` (Redoc), если на сервере не отключена документация.

## OAuth-приложения

OAuth-приложение позволяет стороннему сервису запросить доступ к аккаунтам ваших пользователей. В личных настройках откройте **OAuth-приложения**, затем **Новые OAuth-приложения**:

- **Имя OAuth-приложения**, **Описание**, **URL главной страницы**, **Логотип**;
- **URL обратного вызова** (можно несколько): адрес, на который возвращается пользователь после авторизации приложения;
- **Области применения**: разрешения, которые нужны приложению;
- **Секреты клиента**: **Создать новый секрет клиента**. Секрет виден только при создании. Для каждого секрета отображается дата его последнего использования.

**ID клиента** указан на странице приложения. Поток работает по коду авторизации OAuth 2.0:

1. Приложение перенаправляет пользователя на `GET /api/oauth/authorize` (с `client_id` и `response_type`).
2. Пользователь входит в систему, видит «{имя} запрашивает доступ к вашему аккаунту» с запрошенными областями применения и нажимает **Разрешить**.
3. Приложение обменивает код на токены через `POST /api/oauth/access_token`, аутентифицируясь своим клиентом. Токен обновления позволяет получить новый токен доступа.

Пользователь видит приложения, которым он дал доступ, в **Профиль → Безопасность → Авторизованные приложения** и может отозвать доступ (кнопка отзыва).

| Действие | Маршрут |
|---|---|
| Список, создание приложения | `GET` и `POST /api/oauth/client` |
| Чтение, изменение, удаление | `GET`, `PUT` и `DELETE /api/oauth/client/:clientId` |
| Создание или удаление секрета | `POST /api/oauth/client/:clientId/secret`, `DELETE …/secret/:secretId` |
| Отозвать доступ у всех пользователей | `POST /api/oauth/client/:clientId/revoke-access` |
| Отозвать собственное разрешение | `POST /api/oauth/client/:clientId/revoke-token` |
| Список авторизованных приложений | `GET /api/oauth/client/authorized/list` |

[MCP-сервер](/ru/docs/mcp-server) и [CLI](/ru/docs/cli) также работают через OAuth-сервер TblFlow.

## Сервисные аккаунты

Сервисный аккаунт даёт скрипту, интеграции или CI доступ к пространству, который не зависит ни от одного человека. Он является участником пространства с выбранной ролью (никогда не владельцем), не занимает место в тарифе, а его токены действительны только для этого пространства.

Страница доступна только владельцам пространства: **Настройки пространства → Безопасность и аудит → Сервисные аккаунты**.

1. Введите **Имя аккаунта** и выберите **Роль**: **Читатель**, **Редактор** или **Создатель**, затем нажмите **Создать аккаунт**.
2. Чтобы выпустить токен, укажите **Имя токена**, **Доступ** (**Только чтение**, **Чтение и запись записей** или **Всё, что разрешает роль**) и **Срок действия** 30, 90, 180 или 365 дней, затем нажмите **Выпустить токен**.
3. Скопируйте токен: он больше никогда не будет показан.

Фактический доступ — пересечение областей применения токена и роли аккаунта. **Отозвать** токен или **Удалить** аккаунт можно: действие вступает в силу сразу после подтверждения. В пространстве не более 50 сервисных аккаунтов, у аккаунта не более 20 токенов. Каждое создание, смена роли, выпуск и отзыв записываются в журнал пространства, а владельцы получают письмо до истечения срока токена. [CLI](/ru/docs/cli) использует сервисные аккаунты в непрерывной интеграции.

| Действие | Маршрут (владелец пространства) |
|---|---|
| Список, создание | `GET` и `POST /api/space/:spaceId/service-account` |
| Смена роли, удаление | `PATCH` и `DELETE /api/space/:spaceId/service-account/:serviceAccountId` |
| Выпуск токена | `POST …/:serviceAccountId/token` (`name`, `scopes`, `expiredTime`, необязательный `baseIds`) |
| Отзыв токена | `DELETE …/:serviceAccountId/token/:accessTokenId` |

## Входящие вебхуки

### Запуск автоматизации

[Автоматизация](/ru/docs/automations), у которой триггер — **Когда получен вебхук**, запускается HTTP-запросом:

```bash
curl -X POST "https://app.tblflow.com/api/base/<baseId>/workflow/<workflowId>/webhook" \
  -H "X-Webhook-Secret: <secret>" \
  -H "Idempotency-Key: commande-4821" \
  -H "Content-Type: application/json" \
  -d '{"client": "Ada", "montant": 120}'
```

- Адрес отображается в редакторе автоматизации и в **Автоматизировать → Вебхуки** с кнопкой **Копировать адрес**.
- Секрет обязателен. Без правильного `X-Webhook-Secret` запрос получает ошибку 401. Идентификатора автоматизации недостаточно для аутентификации.
- `Idempotency-Key` (или `X-Idempotency-Key`, не более 255 символов) не даёт обработать одно и то же событие дважды: в ответе тогда приходит `duplicate: true`.
- Ответ `{ "received": true, "queued": true, "eventId": "…" }` приходит сразу после того, как событие сохранено. Если сохранить событие не удалось, сервер отвечает 503: повторите запрос.
- JSON-тело читается из корня в шагах автоматизации.
- Если автоматизация неактивна, запрос получает ответ `{ "received": true, "steps": 0 }` и ничего не выполняет.

Каждый принятый вызов учитывается в месячной квоте запусков автоматизаций.

### Запуск агента

[Агент](/ru/docs/ai-agents) также может иметь триггер **Входящий вебхук**. Запрос: `POST /api/agent/:agentId/webhook` с заголовком `X-Agent-Secret` и JSON-телом. Неверный секрет получает ошибку 401. Ответ — `{ "received": true }`, после чего агент запускается; вызов расходует квоту запусков агента.
