TblFlowのREST APIは、インターフェースと同じデータに、呼び出す本人またはアカウントの権限でアクセスできるようにします。すべてのルートは `/api/` から始まります。このページでは、認証の4つの方法と、受信Webhookを説明します。

| やりたいこと | 方法 |
|---|---|
| ご自身のスクリプトやツール | 個人アクセストークン |
| ユーザーの代わりに動く第三者アプリ | OAuthアプリ |
| 特定の個人に依存しないスクリプト、連携、CI | サービスアカウント |
| 自動化またはエージェントを起動する外部ツール | 受信Webhook |

トークンは `Authorization: Bearer <トークン>` ヘッダーで送信します。

## 個人アクセストークン

個人アクセストークンはご自身の権限で動作し、選んだスコープとスペースまたはベースに限定されます。付与できるのは、ご自身がアクセスできるベースとスペースだけです。

個人設定で **個人アクセストークン** を開き、**新しいトークンを作成** を選びます：

- **名前** と **説明**；
- **有効期限**：7、30、60、90、365日、またはカスタムの日付。どのトークンも365日を超えて有効になることはありません；
- **スコープ**：許可するアクション；
- **アクセス**：1つのベース、1つのスペース（現在および将来のすべてのベース）、または **すべてのリソース**。

トークンは一度だけ表示されます。そのときにコピーしてください。**トークンを再生成** を行うと新しいトークンが作られ、古いトークンを使っているスクリプトは更新が必要です。トークンを削除すると、それを使うスクリプトはAPIにアクセスできなくなります。有効期限の前には、メールで通知されます（14日前と3日前）。メールにトークンが含まれることはありません。

| 操作 | ルート |
|---|---|
| 一覧、作成 | `GET` と `POST /api/access-token` |
| 変更、削除 | `PUT` と `DELETE /api/access-token/:accessTokenId` |
| 再生成 | `POST /api/access-token/:accessTokenId/refresh` |

## APIクエリビルダー

トークンのページから **APIクエリビルダー** のリンクを開くと、`/developer/tool/query-builder` が開きます。ベースとテーブルを選び、ビュー、検索、フィルター、並べ替え、セルの形式を設定してください。**APIビルダー** タブがリクエストを組み立て、戻り値のプレビューを表示します。**AIコンテキスト** タブは、AIアシスタントに貼り付けるテキストを作成します。完全版とコンパクト版があり、アシスタントがそのテーブルの操作方法を理解できるようにします。

## OpenAPIドキュメント

アプリはAPIのOpenAPI記述を生成し、`/docs`（Swagger）と `/redocs`（Redoc）のパスで公開します。ただし、サーバーでドキュメント機能が無効になっている場合は除きます。

## OAuthアプリ

OAuthアプリを使うと、第三者サービスがユーザーのアカウントへのアクセスを要求できます。個人設定で **OAuthアプリ** を開き、**新しいOAuthアプリ** を選びます：

- **OAuthアプリ名**、**説明**、**ホームページURL**、**ロゴ**；
- **コールバックURL**（複数可）：ユーザーがアプリを許可した後に戻される宛先；
- **スコープ**：アプリが必要とする権限；
- **クライアントシークレット**：**新しいクライアントシークレットを生成**。シークレットは作成時にのみ表示されます。各シークレットには最終使用日時が表示されます。

**クライアントID** はアプリのページで確認できます。フローはOAuth 2.0の認可コードです：

1. アプリはユーザーを `GET /api/oauth/authorize`（`client_id` と `response_type` を付けて）へ誘導します。
2. ユーザーはサインインし、「{名前} がお客様のアカウントへのアクセスを要求しています」と、要求されたスコープとともに表示されるので、**許可** を選びます。
3. アプリは、自身のクライアント情報で認証したうえで、`POST /api/oauth/access_token` によりコードをトークンと交換します。更新トークンを使うと、新しいトークンを取得できます。

ユーザーは **プロフィール → セキュリティ → 認可済みアプリ** で、許可したアプリを確認でき、取り消しボタンでアクセスを取り消せます。

| 操作 | ルート |
|---|---|
| アプリの一覧、作成 | `GET` と `POST /api/oauth/client` |
| 読み取り、変更、削除 | `GET`、`PUT`、`DELETE /api/oauth/client/:clientId` |
| シークレットの作成または削除 | `POST /api/oauth/client/:clientId/secret`、`DELETE …/secret/:secretId` |
| 全ユーザーのアクセスを取り消す | `POST /api/oauth/client/:clientId/revoke-access` |
| ご自身の認可を取り消す | `POST /api/oauth/client/:clientId/revoke-token` |
| 認可済みアプリの一覧 | `GET /api/oauth/client/authorized/list` |

[MCPサーバー](/ja/docs/mcp-server)と[CLI](/ja/docs/cli)も、TblFlowのOAuthサーバーを経由します。

## サービスアカウント

サービスアカウントを使うと、スクリプト、連携、CIに、特定の個人に依存しないスペースへのアクセスを与えられます。選んだロールでスペースのメンバーになり（オーナーになることはありません）、シートを消費せず、そのトークンはそのスペースでのみ有効です。

このページはスペースのオーナーのみが利用できます：**スペースの設定 → セキュリティと監査 → サービスアカウント**。

1. **アカウント名** を入力し、**ロール** を選びます：**閲覧者**、**エディター**、**クリエイター**。その後 **アカウントを作成** を選びます。
2. トークンを発行するには、**トークン名**、**アクセス**（**読み取り専用**、**レコードの読み取りと書き込み**、または **ロールで許可されたすべて**）、**有効期間**（30、90、180、365日）を入力し、**トークンを発行** を選びます。
3. トークンをコピーしてください。再び表示されることはありません。

実際のアクセスは、トークンのスコープとアカウントのロールの共通部分です。トークンの **取り消し** やアカウントの **削除** は、確定した時点で有効になります。1つのスペースに作成できるサービスアカウントは最大50、1つのアカウントに発行できるトークンは最大20です。作成、ロール変更、発行、取り消しのたびにスペースのログに記録され、オーナーはトークンの有効期限前にメールを受け取ります。[CLI](/ja/docs/cli)は継続的インテグレーションでこれを使用します。

| 操作 | ルート（スペースのオーナー） |
|---|---|
| 一覧、作成 | `GET` と `POST /api/space/:spaceId/service-account` |
| ロール変更、削除 | `PATCH` と `DELETE /api/space/:spaceId/service-account/:serviceAccountId` |
| トークンの発行 | `POST …/:serviceAccountId/token`（`name`、`scopes`、`expiredTime`、任意で `baseIds`） |
| トークンの取り消し | `DELETE …/:serviceAccountId/token/:accessTokenId` |

## 受信Webhook

### 自動化を起動する

トリガーが **Webhookを受信したとき** に設定された[自動化](/ja/docs/automations)は、HTTPリクエストによって起動します：

```bash
curl -X POST "https://app.tblflow.com/api/base/<baseId>/workflow/<workflowId>/webhook" \
  -H "X-Webhook-Secret: <secret>" \
  -H "Idempotency-Key: commande-4821" \
  -H "Content-Type: application/json" \
  -d '{"client": "Ada", "montant": 120}'
```

- URLは自動化のエディターに表示されるほか、**自動化 → Webhook** の **アドレスをコピー** からも取得できます。
- シークレットは必須です。正しい `X-Webhook-Secret` がない場合は、401エラーが返ります。自動化のIDだけでは認証できません。
- `Idempotency-Key`（または `X-Idempotency-Key`、255文字以内）は、同じイベントを二度処理するのを防ぎます。その場合、レスポンスには `duplicate: true` が含まれます。
- イベントが保存されると、レスポンスは `{ "received": true, "queued": true, "eventId": "…" }` になります。保存に失敗するとサーバーは503を返すので、その場合は再試行してください。
- JSON本文は、自動化のステップでルートから直接読み取れます。
- 自動化が無効な場合、リクエストには `{ "received": true, "steps": 0 }` が返り、何も実行されません。

受け付けられた呼び出しはすべて、自動化の月間実行回数の上限に計上されます。

### エージェントを起動する

[エージェント](/ja/docs/ai-agents)は、トリガーに **受信Webhook** を設定することもできます。リクエストは `POST /api/agent/:agentId/webhook` に、ヘッダー `X-Agent-Secret` とJSON本文を付けて送ります。無効なシークレットには401エラーが返ります。レスポンスは `{ "received": true }` で、その後エージェントが実行されます。この呼び出しは、エージェントの実行回数の上限を消費します。
